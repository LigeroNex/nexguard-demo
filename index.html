The problem

AI agents are stuck at security sign-off.

An agent that can read records, send email or move money is more than a chatbot. Security teams are asked to approve it with no repeatable way to show what it can be made to do.

Agents act, not just answer

They call tools, read records and take actions. A failure is something done, not a wrong sentence.

Ordinary tests miss it

Application security tests and model benchmarks do not cover how a model, its prompts and its tools behave together.

Every change reopens the question

A new model version, prompt, tool or permission can undo last month's approval.

How it works

From blocked to signed off, in six steps.

  1. 01

    Authorise

    Testing starts with written permission and an agreed scope. No permission, no test.

  2. 02

    Map

    List each agent's tools, permissions and the data it can reach.

  3. 03

    Attack safely

    Run versioned attack scenarios in a sealed sandbox, each several times.

  4. 04

    Show the evidence

    Every finding links to the exact steps, versions and run that produced it, and cites the public framework entries it falls under.

  5. 05

    Fix

    Your team tightens the tool, prompt or permission. People decide the severity.

  6. 06

    Retest and sign off

    Re-run to prove the fix holds, then give the approver one evidence pack.

How it is designed

Built for the person who has to say yes.

NexGuard is designed around four ideas.

Evidence an approver can use

Scope, versions tested, every step of a failure and the history of its fix, in one pack.

The same answer every time

The first release uses four fixed checks over the recorded steps, not an AI opinion, so a result can be repeated.

Tests chosen for your agent

Scenarios are picked from what the agent can actually reach, and what was not covered is stated openly.

Contained by design

Attacks run only in an isolated sandbox, with decoy data and mocked tools. Zero escapes is a release rule.

Findings in the vocabulary your team already uses. Scenarios and findings cite the entries they fall under in the OWASP Top 10 for LLM Applications 2026, the OWASP Top 10 for Agentic Applications 2026 and MITRE ATLAS 5.6.0, each pinned to its edition because the numbering changes between editions. A coverage view lists what was exercised and, just as plainly, what was not. There is no score. For the test as a whole, the evidence pack cites NIST AI RMF 1.0 and ETSI EN 304 223, the European Standard that grew out of the UK AI Cyber Security Code of Practice. OWASP, MITRE ATLAS, NIST and ETSI are named for reference; NexGuard is not affiliated with or endorsed by them.

Safeguards

Hard limits, not settings.

A product that attacks AI agents has to be safe to point at your own. These limits cannot be switched off.

  • Permission firstNo test without written authorisation from the system owner and an agreed scope.
  • Sandbox onlyNo attack runs outside an isolated sandbox that is destroyed afterwards.
  • Nothing real happensPayments, messages and deletions are simulated with mocked tools.
  • Decoy dataTests use decoy and synthetic data, not real customer data.
  • Yours aloneFindings and attack detail are never shared between customers.
  • People decideSeverity, accepting a risk and sign-off are decisions for named people.
